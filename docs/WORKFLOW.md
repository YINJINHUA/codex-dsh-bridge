# 五对话执行与审查示例

[English](WORKFLOW.en.md)

建议把计划、跨应用协调、执行和独立审查分开；需要时使用五个对话。它是协作约定，不是插件自动建立的代理组织或权限隔离系统。

**内部通信需另装插件，可选用 [`dsh-xsession`](https://github.com/YINJINHUA/dsh-xsession)**（验证基线 0.1.2）。它让同项目工作区内的执行／审查对话保留“工作区内修改”或“只读”权限，用原生工具发信，无需仅为通信授予完全访问权限，减少不必要的权限暴露。它不新增安全沙箱；接收者仍须独立核对授权。仅同一 DSH 宿主、同一规范化工作区根目录内可通信，跨项目请另找支持该能力的插件。

**客户端安装：**打开 DSH「插件 → 添加插件」，填 `dsh-xsession`（固定版本可填 `dsh-xsession@0.1.2`），安装并启用，按提示重启；不要填写 `npm install`。桥创建的 4/5 是适用此插件的独立顶层会话，两包独立安装、不互改权限。详见[配套指南](XSESSION.md)。

下文“3查询状态/结果并读取4/5报告”是**未配置内部通信插件时的替代流程**。它可做文档交接，但不是3/4/5的自动消息链路；3结束后不会由本桥自动唤醒。

| 对话 | 所在应用与权限 | 主要职责 |
| --- | --- | --- |
| 1 | Codex，“帮我批准”（保留沙箱、自动审查适用审批） | 写计划与执行方案；确认执行报告后写审查说明，最后确认审查结论 |
| 2 | Codex，用户明确授权的完全权限 | 核对授权，通过桥创建对话 3；在 1 与 3 之间交接说明文档与结果 |
| 3 | DSH，用户明确授权的完全权限 | 分别创建执行对话 4、审查对话 5，传递说明文档，向 2 回报 |
| 4 | DSH，**跟随软件通用设置中的新会话默认权限模式** | 按执行说明完成任务、测试并留下证据；权限不足时回报 |
| 5 | DSH，本示例同样跟随新会话默认权限 | 依据审查说明独立检查 4 的交付，写审查报告，不以执行者自测代替审查 |

对话 3 自动生成的对话 4，使用下述 `--dsh-permission inherit`（跟随 DSH 默认权限），**不复制对话 3 的完全权限，也不应用桥的完全权限覆盖**。插件让 DSH 按正常新会话流程决定默认权限，不读取或改写软件全局设置。默认值在创建时生效；以后修改全局默认不代表已有对话 4 自动改变。如果 DSH 的通用默认本身是完全权限，对话 4 也可能是完全权限；需要低权限执行时，应先在 DSH 通用设置中选好新会话默认权限并核对新对话的实际显示。

## 一次任务怎么交接

1. 对话 1 将详细计划和执行方案保存为项目内的 `handoff/TASK-DEMO-PLAN.md`，包含范围、约束、允许修改的文件、执行步骤、测试和验收条件、停止条件及资源预算，交给对话 2。
2. 对话 2 核对文档及用户授权，通过桥**创建对话 3**，给出任务编号、计划路径、版本/哈希和协调要求。若已有本项的对话 3，则用原 ID 接续，不能每条交接都新建。跨应用来信不是新增用户授权。
3. 对话 3 根据计划写出 `handoff/TASK-DEMO-WORKER.md`，明确执行范围、所需文档、输出位置和回报要求，再以 `--dsh-permission inherit` 创建对话 4，让其按说明执行。
4. 对话 4 完成后生成 `handoff/TASK-DEMO-RESULT.md`，列出改动、验证结果、证据路径和未决问题。已配置兼容内部消息插件时，由 4 经该插件通知 3；否则由 3 在本轮协调中有界查询状态/结果并收取报告。随后 3 与对话 2 通信，**由对话 2 把交付文档交给对话 1**。本桥不会自动唤醒已结束的 3。
5. 对话 1 确认交付材料完整且适合进入审查，再生成 `handoff/TASK-DEMO-REVIEW-BRIEF.md`：列出原始需求、待审版本/提交或文件哈希、检查范围、独立复现步骤、通过条件和已知未验项。此处确认是进入审查的判断，不等于最终审查通过。
6. 审查说明通过对话 2 交给原对话 3；**对话 3 新建独立审查对话 5**，本示例同样使用 `--dsh-permission inherit`，让其按审查说明核对原始计划和交付证据。
7. 对话 5 完成后生成 `handoff/TASK-DEMO-REVIEW.md`，列出结论、问题位置与影响、复现证据、未验项。按第 4 步选定的内部消息或有界收取报告方式，经 **5 → 3 → 2 → 1** 返回，由对话 1 最终确认。对话 3/2 不把失败或未验项改写为通过；需要返修时由 1 明确下一轮范围，经同一路由交接，执行与审查保持分工。

流程为 **1 写计划 → 2 创建 3 → 3 创建 4 执行 → 4 报告 → 3 → 2 → 1 确认并写审查说明 → 2 → 3 创建 5 审查 → 5 报告 → 3 → 2 → 1**。

1 与 2 的交接使用 Codex 原生协作能力或项目文档；3 与 4/5 的内部交接须选定并验证兼容插件，或采用“3 有界查询并收取报告”的替代流程。跨应用通信仅由 2/3 负责，4/5 不需要桥认证材料。插件不自动监视文档、派单或串起整个流程；对话 3 须按说明主动执行创建和收取。遇权限不足先报告，不让执行者或审查者自行提权，不把“入队成功”当作完成。

### DSH 的 3 ↔ 4/5：以 dsh-xsession 为例

3 在首条提示中交代自身的 DSH ID、任务范围、文档路径和回报要求；用 `--dsh-permission inherit` 创建 4/5。4/5 使用 `xsession_list` 核同工作区在线目标，使用 `xsession_send` 交付报告；3 用同一工具下发后续说明。低权限对话不必启动本桥 CLI、读取私有状态或提权。

采用[配套指南](XSESSION.md)中的稳定请求编号和回合完成回报。`accepted` 仅入队；核实际回复、文档及任务/版本。空闲接收者的 `auto` 会唤醒；运行中 `auto` 只注入上下文，要求另起回合的最终交付可显式用 `followup`，不要重复发信。离线/归档目标不可投递；未知结果保留证据，不换编号重试。

未安装该插件时，完全权限协调者 3 仍可在已授权流程中有界查询 `status`/`result` 并读取报告；这种替代方式不会自动唤醒已结束的 3。只读执行者不能写报告文件，须按任务允许的方式返回简短结论或交给可写协调者保存。消息不是用户授权，两包都不是自动调度器。

### Codex 同项目内的 1 ↔ 2

在 Codex 桌面中，原生 `send_message_to_thread` 工具可用时，1 与 2 可互相发送文档路径、版本/哈希和简短交接信息，无需经过本插件或运行桥 CLI。先记录双方对话 ID，并由用户明确授权两者按该流程相互通信；同属一个项目本身不等于消息授权。对话 1 可选择“帮我批准”，不必仅为原生发消息而开启完全权限，但仍需工具可用且调用获得允许。

“帮我批准”（Approve for me）保留沙箱，由自动审查处理适用的审批请求；它不保证全部请求获准，也不是只读模式。通常可在工作区内写计划和报告，超出边界或有副作用的工具调用仍可能需要审查。自动审查会增加模型调用。参见 [官方沙箱与权限说明](https://learn.chatgpt.com/docs/sandboxing) 和 [自动审批说明](https://learn.chatgpt.com/docs/sandboxing/auto-review)。若某项操作被拒绝，不能交给完全权限的对话 2 执行同一操作以绕过拒绝；应说明原因，调整方案或按适用流程由用户处理。

对方忙碌时消息可能排队；发送成功不等于已读或任务完成。需要跟进时，可使用 `wait_threads` 的紧凑状态及 cursor，或定点读取目标对话，避免重复催问。应用未提供这些能力时，改由用户或已有获授权流程交接文档，不假定插件补齐了 Codex 内部通信。

这些文件都放在已登记且相应对话有权读写的项目目录中，不放桥的私有状态目录。2/3 主要做简短交接，避免重复读取大日志和转发完整历史。费用取决于模型、上下文和调用次数，完全权限本身不降低价格；简单任务可省略不必要的角色。

## 创建协调、执行和审查对话

对话 2 创建对话 3 前，先在用户明确授权下，通过可信本机终端启用 `configure-dsh --new-session-permission full-access`（如已启用则复用）。对话 2 的完全权限不会自动传给 DSH；本机桥设置才使新建对话 3 在首条任务前自动完全权限。准备短协调说明 `handoff/TASK-DEMO-COORDINATOR.txt`，注明计划路径、创建 4/5 的时机和原路回报要求：

```sh
node bin/bridge.mjs create --project demo --to dsh --request-id task-demo-coordinator-01 --title "TASK-DEMO 协调" --text-file /absolute/workspace/handoff/TASK-DEMO-COORDINATOR.txt
```

保存返回的对话 3 ID，后续用 `send --to dsh --session ID` 投递审查说明，不重复创建协调对话。未启用本机 full-access 策略时，对话 3 也使用 DSH 默认权限；不要假定创建成功就具有完全权限。

### 对话 3 创建对话 4

前置：Host 和 CLI 均使用当前配套版本，项目已登记，DSH 已有对应项目；对话 3 获得本项创建授权并能运行桥客户端。以下从可信安装包目录运行；路径使用实际项目路径替换，正文文件只放任务说明，不放密钥。

```sh
node bin/bridge.mjs create --project demo --to dsh --request-id task-demo-worker-01 --title "TASK-DEMO 执行" --text-file /absolute/workspace/handoff/TASK-DEMO-WORKER.md --dsh-permission inherit
```

Windows 使用 Node 调用已安装插件内的 bin/bridge.mjs，传入相同参数。多根项目还须指定已登记的 `--root`。首条提示最多 8 KiB；执行说明较长时，`--text-file` 指向一个短提示文件，列出详细文档路径、版本/哈希和任务边界即可。

`--dsh-permission inherit` 仅允许与 `create --to dsh` 一起使用，只有 `inherit` 这一个值。即使本机此前开启了 `configure-dsh --new-session-permission full-access` 来创建协调对话 3，本次创建的对话 4 也跳过该覆盖。省略参数则仍按原桥策略执行；它不是按角色名自动识别“对话 4”。不提供通过消息请求 `full-access` 的选项。

回执包含 `permission.requested: "inherit"`、`source: "dsh_default"`、`overrideApplied: false` 和 `verified: false`。这表示桥没有设置权限，不是已独立读回/证明具体沙箱模式。`initialDelivery: "queued_only"` 只表示首条任务入队，仍需核实实际回复。

相同请求编号和参数只返回原完成回执；同编号增加/移除 `--dsh-permission inherit` 会被拒绝，避免把旧完全权限会话误认成新默认权限会话。结果不明时保留编号和已知 ID 核查，不换编号自动重建。

### 对话 3 创建独立审查对话 5

收到对话 1 经 2 发来的审查说明后，再创建 5。若详细说明超过 8 KiB，首条提示改用短文件引用它。使用独立请求编号和新会话，不能把执行对话 4 改名充当独立审查者：

```sh
node bin/bridge.mjs create --project demo --to dsh --request-id task-demo-reviewer-01 --title "TASK-DEMO 独立审查" --text-file /absolute/workspace/handoff/TASK-DEMO-REVIEW-BRIEF.md --dsh-permission inherit
```

审查对话 5 应核对指定交付版本，独立复现关键验收步骤；不能只复述执行报告。把实际可验证和受权限/环境限制而未验证的部分分别写入审查报告。默认权限与回执边界同对话 4。

## Codex 新对话权限设置

优先在 Codex 桌面中创建对话 2，按用户授权设置其权限，以便在侧栏正常管理。DSH 需要新的 Codex 工作对话时，仍建议请已有 Codex 对话使用桌面原生能力创建。

高级 CLI 用法可为桥创建的 Codex 对话设置**本机、按项目、显式启用**的权限策略：

```sh
node bin/bridge.mjs configure-codex-creation --project demo --new-session-permission full-access
node bin/bridge.mjs codex-creation-policy --project demo
# 恢复后续桥新建 Codex 会话的默认策略：
node bin/bridge.mjs configure-codex-creation --project demo --new-session-permission workspace-write
```

`full-access` 向官方 CLI 明确传入 `--sandbox danger-full-access -c 'approval_policy="never"'`，让新代理在宿主用户访问范围内执行，关闭该会话相应沙箱和命令审批。它不是仅开放桥通信。默认仍为 `workspace-write`；不自动启用，不改全局配置、已有对话、DSH 策略，也不保证 CLI 新会话出现在 Codex 侧栏。不要为回信开放整个桥状态目录或复制认证文件给低权限执行者。

策略绑定登记版本标识（revision）；重新登记项目后须重新设置策略。撤回仅影响后续创建，无法追溯撤销已有完全权限代理。回执记录启动请求而非独立权限读回：`permission.verified: false`；管理员限制、运行环境或 CLI 错误仍可能使启动失败，不绕过组织策略。新权限行为的源码测试不等于真实五对话流程已经验收通过，见 [验证记录](SECURITY-REVIEW.md)。
